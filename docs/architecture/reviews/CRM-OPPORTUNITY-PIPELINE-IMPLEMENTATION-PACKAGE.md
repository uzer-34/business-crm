# CRM Opportunity and Pipeline implementation package

**Prepared:** 2026-10-11

**Status:** Decision package for review; no schema, migration, permission, or production implementation is authorized by this document.

This package closes the local architecture review for the accepted first CRM slice. It supplements the [decision register](../decisions/CRM-GATE0-DECISION-REGISTER.md), [Opportunity/Pipeline proposal](../decisions/CRM-OPPORTUNITY-PIPELINE-PROPOSAL.md), [Gate 0 readiness review](CRM-GATE0-IMPLEMENTATION-READINESS-REVIEW.md), and [audit/idempotency proposal](../decisions/CRM-AUDIT-IDEMPOTENCY-PROPOSAL.md). Accepted boundaries remain: reuse Customer/LEAD and its IDs; CRM owns Opportunities; Pipeline owns reusable published versions, stages, transitions, enrollments, and history; only configured open-to-open transitions; no quotes, orders, terminal outcomes, reassignment, event delivery, or outbox.

## Repository facts and current boundary

- `prisma/schema.prisma` has Customer, Task, Activity, Membership, and AuditLog; it has no Opportunity or Pipeline models. Customer already has `organizationId`, nullable `branchId`, nullable `assignedToId`, and `LEAD` status. Task has nullable `customerId` and `assignedToId`. Activity has a polymorphic `subjectType`/`subjectId` pair and nullable `customerId`. AuditLog is a separate security record.
- `src/lib/rbac/permissions.ts` has no Opportunity or Pipeline permission keys. Owner templates are generated from the full current permission catalog. Manager and Employee grants are explicit lists; Employee has `allBranches: false`. Custom roles are explicit organization-specific subsets. These are source-template facts; deployed grants have not been inspected.
- `src/lib/crm/enrollment.ts` validates same-organization Customer, active same-organization owner, published version, and open entry stage. `src/lib/crm/pipeline-transition.ts` validates the pinned version, open stages, and directed edges. It now also requires the pinned version to be marked published. These pure validators do not authenticate, authorize, query the database, or establish tenant security.
- Gate 0 remains pending. PostgreSQL deployment facts, database roles/grants, resolver privileges, production catalog, RLS, backup/PITR recovery, migration window, and recovery owner have not been verified. No live database was accessed.

## Minimal typed data design for review

The following is a logical design, not Prisma or migration code. Every tenant-owned relation carries `organizationId`; every cross-model FK uses organization-consistent keys. Exact SQL names, Prisma relation shape, and generated SQL must be reviewed together before implementation.

| Record | Minimum identity and relation contract | Constraints and indexes | Delete / mutability proposal |
| --- | --- | --- | --- |
| `Pipeline` | `id`, `organizationId`; organization-level reusable definition. No branch-specific configuration in this slice. | `UNIQUE (organizationId, id)`. Index by organization and any approved archive/list state. | Archive rather than delete after versions exist. Hard delete restricted when versions refer to it. |
| `PipelineVersion` | `id`, `organizationId`, `pipelineId`, monotonically distinguishable version number, draft/published state, `publishedAt`, and one configured `entryStageId`. | FK `(organizationId,pipelineId)` to Pipeline. `UNIQUE (organizationId,id)` and `UNIQUE (organizationId,id,pipelineId)`. `UNIQUE (organizationId,pipelineId,versionNumber)`. Entry-stage FK must include organization and version. A published version must have a valid open entry stage. | Drafts may be edited; publication freezes version, stage, entry-stage, and transition definitions. New changes create another version. Restrict deletion when enrolled or referenced by history. |
| `PipelineStage` | `id`, `organizationId`, `pipelineVersionId`, display name/order, and status. First-slice enrollment and transitions use OPEN stages only. | `UNIQUE (organizationId,pipelineVersionId,id)`; stage ordering unique within a version if product chooses a stable ordering rule. Stage-to-version FK includes organization. | Published stages immutable. Restrict deletion when referenced by entry-stage, transitions, enrollment, or history. |
| `AllowedPipelineTransition` | `organizationId`, `pipelineVersionId`, `fromStageId`, `toStageId`. Directed edge; no generic workflow/action payload is needed for this slice. | FKs `(organizationId,pipelineVersionId,fromStageId/toStageId)` to stages in the same version; unique directed edge; check `fromStageId <> toStageId`. | Immutable with the published version; referenced version/stages are restricted from deletion. |
| Parent-key prerequisites | Add `UNIQUE (organizationId,id)` to Customer and Branch for tenant-consistent relations; Customer currently has no such composite key and Branch currently has only an organization index. Membership already has `UNIQUE (id,organizationId)`. | Use FK `(organizationId,customerId)` → Customer `(organizationId,id)`; `(organizationId,branchId)` → Branch `(organizationId,id)`; and `(ownerMembershipId,organizationId)` → Membership `(id,organizationId)`. Keep referenced-column order aligned with each unique key. | Preflight duplicate parent keys before adding constraints; preserve every existing Customer ID. |
| `Opportunity` | CRM-owned `id`, `organizationId`, non-null `customerId`, nullable `branchId`, non-null `ownerMembershipId`, timestamps/archive state. Additional business fields such as title/value/date/source remain a product field-set decision. | `UNIQUE (organizationId,id)` and `UNIQUE (organizationId,id,customerId)`. FKs use the parent-key prerequisites above. No unique Customer/title constraint: multiple Opportunities per Customer are allowed. | Archive Opportunities. Restrict hard Customer delete while an Opportunity exists. Owner must be active; FK alone cannot enforce Membership status, so creation/assignment and membership suspension/removal need transactional application checks. |
| `OpportunityEnrollment` | One current row per Opportunity: `id`, `organizationId`, `opportunityId`, pinned `pipelineVersionId`, current `stageId`, integer `version` for compare-and-swap, timestamps. | `UNIQUE (organizationId,opportunityId)`; FKs `(organizationId,opportunityId)` to Opportunity, `(organizationId,pipelineVersionId)` to version, `(organizationId,pipelineVersionId,stageId)` to stage. This singular row represents the one active enrollment; reassignment/history of enrollments is out of scope. | No cascade that erases history. Opportunity/version/stage deletion is restricted. Enrollment changes only through approved transition commands. |
| `StageTransitionHistory` | `id`, `organizationId`, `enrollmentId`, pinned version, from/to stage IDs, actor user and membership, UTC time, resulting enrollment version, command type, idempotency key, normalized request fingerprint, and approved correlation metadata. | Typed FKs to same-organization enrollment and both stages within its pinned version. `UNIQUE (organizationId,commandType,idempotencyKey)`. Index history by organization/enrollment/time. The idempotency record is retained with the history so retries can return the original result. | Append-only in application behavior; no cascade from Opportunity, enrollment, version, or stage. Database immutability requires separately reviewed grants/triggers and is not claimed here. |

Published immutability is an application and database-write-boundary obligation; a status column alone does not prevent edits. A future migration must choose and verify a suitable enforcement method (restricted writer path/role or a reviewed database trigger) without assuming the deployed role model. An enrollment's pipeline version is pinned and cannot be changed by the first slice.

### Task and Activity nullable Opportunity links

Preserve the existing nullable `Task.customerId` and existing `Activity.customerId` exactly as nullable. Add nullable typed `opportunityId` columns; no generic `subjectType`/`subjectId` pair is accepted as the only Opportunity relationship.

| Table | Proposed database relationship | Rules |
| --- | --- | --- |
| Task | Keep `organizationId`; keep Customer FK `(organizationId,customerId)` to `Customer(organizationId,id)` with current `ON DELETE CASCADE`; add nullable `opportunityId` and composite FK `(organizationId,opportunityId,customerId)` to `Opportunity(organizationId,id,customerId)` with `ON DELETE RESTRICT`. Add index `(organizationId,opportunityId)`. | `customerId` remains independently nullable when `opportunityId IS NULL`, preserving standalone Tasks. `CHECK (opportunityId IS NULL OR customerId IS NOT NULL)`. When opportunityId is set, the Customer must be that Opportunity's Customer in the same organization. A Customer cascade is naturally blocked by the Opportunity FK when the Task is Opportunity-linked. |
| Activity | Keep `organizationId`, polymorphic subject fields, and nullable `customerId`; add nullable `opportunityId`. Keep a tenant-consistent Customer FK with current `ON DELETE CASCADE`; add composite FK `(organizationId,opportunityId,customerId)` to Opportunity with `ON DELETE RESTRICT`; add index `(organizationId,opportunityId)`. | Existing non-Opportunity Activity subjects retain current behavior. For an Opportunity activity, require `opportunityId IS NOT NULL`, `customerId IS NOT NULL`, `subjectType = 'Opportunity'`, and `subjectId = opportunityId`. A SQL CHECK must enforce both directions (typed ID set iff Opportunity subject) and prevent Opportunity-without-Customer. Existing Customer-only and other-subject rows may keep nullable Customer links as they do now. |

The FK plus checks reject cross-tenant references, a Task/Activity pointing at an Opportunity for another Customer, an Opportunity link without its Customer, and an Opportunity Activity whose polymorphic subject disagrees with its typed ID. The proposed Prisma compound relations use scalar organization/customer fields already present; isolated Prisma validation previously confirmed that shape, but does not prove these SQL checks, deployed data, delete behavior, or authorization.

### Preflight, migration, rollback, and forward-fix

Before creating a migration, require Gate 0 evidence, named DBA/recovery owner, approved write pause/window, tested backup/PITR restore, and separate implementation authorization. Do not run against Neon production as part of this package.

Read-only preflight must report counts and sanitized identifiers for:

1. Every existing direct-ID relationship where parent organization differs from child organization (at minimum Task→Customer, Activity→Customer, Order/Invoice/Vehicle and the other tenant-owned links inventoried in Gate 0).
2. Task/Activity rows with Customer mismatch; Activity Opportunity polymorphic subjects, if any; duplicate or orphan identifiers; and any branch or Membership organization mismatch.
3. Existing Customer IDs and row counts to prove migration preserves identity and behavior; duplicate candidate composite keys before unique constraints.
4. New Opportunity enrollment coverage, owner activity, published-version entry-stage validity, and stage graph consistency before any transition data is accepted.

For authorized implementation, use an expand/validate/contract sequence fit to verified PostgreSQL and traffic: add nullable typed fields/keys/indexes; remediate preflight findings only under reviewed ownership rules; add tenant-consistent FKs and checks; validate constraints; deploy application reads/writes only after validation. No historical `opportunityId` backfill is expected because no Opportunity model exists in this checkout. Do not silently rewrite tenant ownership.

Prefer forward-fix for additive schema changes. A rollback plan must identify whether the old application remains compatible with additive columns and constraints; do not drop data or constraints as an automatic rollback. Recovery owner decides rollback versus forward-fix from the tested runbook. Retain migration logs, preflight counts, approvals, validation output, and recovery sign-off. Exact lock/statement behavior must be confirmed for the actual PostgreSQL version and hosting/pool mode.

## Stage-transition transaction contract

The accepted boundary is one PostgreSQL transaction containing the enrollment update, transition history, Activity, and AuditLog. Authorization runs on the server from trusted tenant context; an organization ID from request input is never trusted. Database constraints remain the final relationship guard once approved.

1. Validate request shape and canonicalize the approved payload. The fingerprint covers organization, actor membership, command type, Opportunity, pinned pipeline version, expected enrollment version/current stage, target stage, and all approved semantic fields. Do not include unapproved free-form request bodies.
2. Resolve active membership, capability, branch and owner access, and eligible active Opportunity owner. Load the Opportunity, enrollment, pinned version, stages, and allowed edge under the authenticated organization. The version must be published and match the enrollment; only an explicitly configured OPEN→OPEN directed edge is accepted.
3. Check `(organizationId,commandType,idempotencyKey)`. If an existing record has the same normalized fingerprint, return the original transition result without additional writes. If the key exists with another fingerprint, return a conflict. Authorization and current access are still checked before returning stored data.
4. Conditionally update enrollment where organization, enrollment ID, expected current stage, and expected integer version match. Increment version exactly once. Zero updated rows means stale-state conflict; do not reload and silently apply the requested edge to a different state.
5. In the same transaction, append transition history, one Activity describing the user-facing stage change, and one AuditLog security record with approved, minimized metadata. Keep Activity separate from AuditLog; neither replaces typed history. No event bus or outbox write is part of this slice.
6. Commit only after all writes succeed. Any FK/check failure, unique-key race, Activity/AuditLog failure, or application error rolls the whole transaction back; enrollment state cannot commit alone.
7. For concurrent same-key requests, let the unique constraint select one committed history row. The losing request reads that row in a fresh transaction, compares the fingerprint, and returns the prior result or conflict. Do not treat arbitrary database errors as a replay. Different-key concurrent transitions from one version yield one success and one stale conflict.

The stable public conflict categories should distinguish stale expected state, idempotency key/payload mismatch, disallowed edge, and unauthorized/out-of-scope access without revealing foreign-tenant record existence. Error status/body format remains an API decision before UI implementation.

## Verification contract

**Completed locally in this package:** pure unit coverage for valid directed open transitions, reverse-edge directionality, missing edges, same-stage requests, wrong pinned version, malformed/duplicate/self edges, terminal stages, deterministic results, and input immutability. The validator additionally rejects unpublished pipeline versions and missing/malformed publication state.

**Required after Gate 0 and separate implementation authorization:**

- Tenant/branch/owner/capability integration checks for read, create, edit, assignment, transition, null-branch records, and foreign IDs.
- DB constraint tests for every composite FK/check above; multiple Opportunities per Customer; one enrollment per Opportunity; active same-tenant owner validation; version/stage pin consistency; Task and Activity nullable combinations; and RESTRICT/CASCADE behavior.
- Transaction tests proving stale compare-and-swap, same-key/same-payload replay, same-key/different-payload conflict, two different keys racing, and rollback after failure at enrollment/history/Activity/AuditLog writes.
- Migration tests against a representative copy of the exact schema and data assumptions, preflight on sanitized real catalog evidence, plus recovery rehearsal. No production-readiness claim from unit tests alone.

## Remaining approvals and blockers

1. **Product / Identity-RBAC:** approve or edit each capability name and Owner/Manager/Employee/custom-role mapping; settle view-all, manage-all, branchless creation, assignment scope, and linked Task permissions. This blocks CRM permission enforcement.
2. **CRM / Data architecture / DBA:** review and approve the precise composite FK, Activity checks, and deletion contract above. This blocks schema/migration work.
3. **Security / Platform / DBA / Recovery owner:** close all Gate 0 evidence and explicitly approve Gate 0. Deployment facts, PostgreSQL/catalog/role grants, resolver privileges, RLS, backup/PITR, write pause, recovery owner, migration checklist, and module scope are not established by repository inspection.
4. **User/Product owner:** issue separate implementation authorization after the preceding approvals. This package itself does not grant it.

Until then, do not add RBAC keys, Opportunity/Pipeline models, schema changes, migrations, RLS policies, UI, terminal outcomes, quotations, orders, or event delivery. The safest next implementation task after approvals is the additive schema migration plus focused database integration tests for tenant keys and Task/Activity constraints, followed by the authorized Opportunity/enrollment service.
